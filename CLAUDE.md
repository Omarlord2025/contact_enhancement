# Engineering Standards — contact_enhancements

This file is read automatically at the start of every Claude Code session in this repo and is treated as ground truth. Every new function, feature, or script added here must satisfy this checklist before it's considered done.

## 1. Domain gotchas — read this before touching Customer/Contact/Lead linking

- **A Report/Workspace/Print Format JSON belongs one directory deeper than it looks** - confirmed the hard way adding the "Duplicate Mobile Contacts" report and "Contact Enhancements" workspace. This app's only module is "Contact Enhancements" (`modules.txt`), so Frappe's real convention is `<app>/<app>/<module_scrubbed>/<doctype_folder>/<name>/<name>.json` - three `contact_enhancements` levels deep (app root, package, module folder), not two. Putting `report/`/`workspace/` directly under the package root (`contact_enhancements/contact_enhancements/report/...`) fails silently: `bench migrate` reports success and neither `bench --site <site> reload-doc <app> <doctype-folder> <name>` nor the record itself errors - it just never creates the DB row, because `frappe.modules.get_module_path()`-based discovery never looks there. Verify a new fixture actually landed with a direct query (`SELECT name FROM \`tabReport\`/\`tabWorkspace\` WHERE name=...`), not just an exit code of 0. A Python-side module import path for code alongside it (e.g. `report/duplicate_mobile_contacts/duplicate_mobile_contacts.py`) needs the same extra `contact_enhancements.` prefix segment.
- **Editing an already-synced Workspace/Report/Print Format JSON a second time needs its `modified` timestamp bumped**, confirmed against the exact same gotcha already documented in this bench's own `wheel_tracker/CLAUDE.md`: sync for these doctypes is gated purely on `file.modified > db.modified` (`frappe/modules/import_file.py`), not a content hash the way DocType JSON is. The very first sync always works (no DB row yet to compare against), but a later edit with an unchanged or older timestamp is skipped with no error and no warning - `bench migrate` still reports success. Set `modified` to something newer (`date -u +"%Y-%m-%d %H:%M:%S.%6N"`) on every edit after the first, and confirm with `frappe.db.get_value(doctype, name, "modified")` that it actually moved.
- **Once `add_contact_phone_unique_mobile_index`'s UNIQUE INDEX is actually live on a site, no test can construct two genuinely-colliding `Contact Phone` rows anymore - not even via a raw `frappe.get_doc({...}).db_insert()`, and not via `SET unique_checks=0` either (confirmed directly: MariaDB still raises `IntegrityError` through that session variable for a real UNIQUE INDEX violation - it does not suppress it the way it can for some bulk-load scenarios).** This is by design (the whole point of Phase 0d), but it permanently breaks any test fixture built on "insert a second conflicting row and see what the code does with it" - discovered when `bench migrate` finally succeeded on a real site and the next full test run immediately failed ~22 tests that all depended on `tests/test_contact_dedupe.py`'s own `_add_duplicate_phone` helper. Fix used throughout this app's own tests: mock at the query boundary instead of writing real conflicting rows -
  - `find_duplicate_mobile_contacts()` / `find_duplicate_phone_rows_within_contact()` (self-contained, one `frappe.get_all` call each): patch `contact_enhancements.api.contact_dedupe.frappe.get_all` with a `return_value` of synthetic `frappe._dict(...)` rows.
  - `classify_contact_duplicate()` / `warn_if_duplicate_contact()` / `merge_duplicate_mobile_contacts()` (all call `find_contacts_by_phone` internally): patch `contact_enhancements.api.contact_dedupe.find_contacts_by_phone` directly - every Contact involved can and should still be a real, saved Contact, so the rest of the function's own real behavior (an actual `frappe.rename_doc` merge, an actual delete) is still exercised for real.
  - `dedupe_contact_phone_rows()` (calls `frappe.get_doc("Contact", contact)` itself, no query to fake): patch `contact_enhancements.api.contact_dedupe.frappe.get_doc` with a **narrow `side_effect`** that only intercepts the exact `("Contact", <name>)` call this function makes and falls through to the real `frappe.get_doc` otherwise - never a blanket `return_value`. Confirmed the hard way: a blanket mock also intercepts `Document.check_if_latest()`'s own internal `frappe.get_doc(..., for_update=True)` re-read (used for optimistic-locking / `TimestampMismatchError` detection), silently corrupting it too, since `frappe.get_doc` is one shared, module-level attribute - not something scoped per caller. The same applies to a hand-rolled counting/spy wrapper around `frappe.get_doc` (e.g. to assert "this function doesn't reload a doc I already passed it") - exclude any call with `for_update=True` from the count, or a legitimate `.save()` triggered *inside* the function under test gets misread as an extra, unwanted load (`tests/test_utils.py`'s own `test_reuses_a_passed_in_contact_without_reloading`).
  - `enforce_unique_mobile_number` (in `contact_hooks.py`, not `contact_dedupe.py`) still patches at `contact_enhancements.api.contact_dedupe.find_contacts_by_phone` even though it's called from a different module - its own `from contact_enhancements.api.contact_dedupe import find_contacts_by_phone` is a *local* import inside the function body, re-resolved fresh on every call, so it picks up whatever's currently patched at the *origin* module regardless of where it's imported into.
- **Reusing an already-`.insert()`-ed Document object for a second `.save()` in the same test needs `doc._original_modified = doc.modified` set explicitly first, or `check_if_latest()` raises a spurious `TimestampMismatchError`.** Confirmed by reading `Document.set_user_and_timestamp()`: `_original_modified` is a plain instance attribute set in exactly two kinds of place in core Frappe - inside `set_user_and_timestamp()` itself (called *during* a save, so it only reflects whatever `.modified` was *before that specific save*, not "what's currently in the database"), and explicitly by REST-layer callers (`frappe/handler.py`, `frappe/api/v2.py`) right before invoking `.save()` on a doc they just loaded for a client. A plain `frappe.get_doc(...)` never sets it at all. A doc object that only ever went through one `.insert()` still has it stuck at that insert's own *pre-insert* value (typically `None`), so a later, separate `.save()` on that same object compares the database's real `modified` against that stale value and always "mismatches" - stamp it yourself first, the same way the REST handlers do.

- **A shared field like `mobile_no`/`email_id` on Customer/Supplier syncing from a linked Contact is native Frappe (`fetch_from` on the field itself, e.g. Supplier.mobile_no's `"fetch_from": "supplier_primary_contact.mobile_no"`, confirmed by reading each doctype's own JSON directly) - already identical for every doctype with that field, nothing this app needs to build.** What this app *does* still have to build, per doctype, is a field-change handler on the primary-contact field itself (e.g. `supplier_primary_contact(frm) {...}` in supplier.js) that live-prefills anything the linked Contact doesn't natively carry (Supplier/Customer's own name, in particular) - and that handler has to fire for *every* way the field can end up set (picking an existing Contact via the dialog's own search, via the native Link field's dropdown directly, or creating a new one through the dialog), not just the dialog's own "Create New Contact" path. Confirmed the hard way: Phase 1's first cut of supplier.js only ever set `supplier_name` inside the dialog's own `on_before_finish` (create-path only), leaving it blank whenever an *existing* Contact was picked instead - customer.js's own `customer_primary_contact(frm)` handler already got this right by relying on the field's own change event, not dialog-specific logic, for exactly this reason. `frm.set_value(primary_contact_fieldname, ...)` (called from the shared dialog's own `finish()`) does trigger that registered field handler correctly regardless of which path triggered it - the field handler doesn't need any special-casing for "did this come from the dialog."
- **Dynamic Link vs plain Link.** `Customer.customer_primary_contact`/`customer_primary_address` are plain Link fields, completely unrelated to the Dynamic Link mechanism Contact/Address's own `links` child table uses. ERPNext's own `Customer.link_address_and_contact()` only ever creates the Dynamic Link when converting a Lead/Opportunity/Prospect — it never sets `customer_primary_contact`/`customer_primary_address` themselves. That gap is exactly why `customer_hooks.py` backfills them explicitly in `validate()`; don't assume any native ERPNext conversion flow populates these fields for you.
- **`mandatory_depends_on` is client-side only** in this Frappe version — confirmed by reading `frappe.model.base_document.BaseDocument._get_missing_mandatory_fields`, which only ever iterates fields with the static `reqd` flag and never consults `mandatory_depends_on`. It drives the browser's own pre-save "Missing Fields" check and nothing else. Real, API/Data-Import-proof enforcement needs an explicit `frappe.throw` inside a `validate()` doc_event (see `contact_hooks.enforce_identity_field_is_present`-style checks) — never assume setting the JSON property alone makes a field genuinely required.
- **Quick Entry's `doctype_js` timing gap.** A doctype's `doctype_js` content only gets evaluated once a real `frappe.ui.form.Form` is constructed for it (`frappe.ui.form.ScriptManager.setup()` reads it off `frm.meta.__js`) — but Quick Entry never constructs one until *after* its own "show Quick Entry or full form" decision is already made. A client-side `is_quick_entry()` override placed in a doctype's own JS file can never intercept that decision — confirmed by testing directly. Disabling Quick Entry needs a Property Setter on the doctype-level `quick_entry` property, not JS.
- **Frappe's own client-side mandatory-field check runs *before* the save request is ever dispatched to the server** - confirmed the hard way building Customer's own address auto-resolve (customer_hooks.sync_customer_from_primary_contact's cross-doctype fallback): a server-side validate() hook that fills in a mandatory field is *never given the chance to run* if that field is still blank in frm.doc at the moment Save is pressed, because Frappe's own native mandatory check inspects frm.doc directly and blocks locally - the request is never sent at all. A client-side validate() handler that checks the same field has the identical problem for the same reason. The fix is to make whatever the server would have auto-resolved happen client-side too, proactively, the moment the deciding field changes (see public/js/customer.js's own customer_primary_contact handler calling the whitelisted api.contact_lookup.get_address_from_contact_links and frm.set_value()-ing the result) - by the time the user clicks Save, the field is already genuinely set, not just about to be. Any future "auto-resolve field X from field Y" feature on a *mandatory* field needs this same client-side mirror, not just a server-side validate() hook - the hook alone is sufficient for a non-mandatory field (nothing blocks the request from reaching the server-side resolve), but never for a reqd one.
- **The native `frm.add_fetch(...)` async race.** ERPNext's own `customer.js` registers `frm.add_fetch("lead_name", "company_name", "customer_name")`. Setting `lead_name` (even programmatically via `frm.set_value`) kicks off a *detached* `frappe.xcall("frappe.client.validate_link", ...)` that is NOT covered by that `set_value()` call's own returned promise — confirmed empirically with a stack trace (`update_dependant_fields` in `frappe/public/js/frappe/form/controls/link.js`) and by reproducing the bug (a value set correctly, then silently overwritten moments later). The only reliable way to sequence after it is `await frappe.after_ajax()` before applying anything that depends on the field you just set — reordering `set_value` calls alone does not fix this.
- **Property Setter / Custom Field Patch Log staleness.** Editing a function in `setup/custom_fields.py` or `setup/property_setters.py` after its corresponding patch has already run once does **not** get picked up by `bench migrate` — Frappe's Patch Log marks a patch "applied" by name, permanently. While iterating locally, re-invoke the function directly: `bench --site <site> execute contact_enhancements.setup.<module>.<function_name>`.
- **A `search_index` (or any schema-affecting) Property Setter needs an explicit `frappe.db.updatedb(doctype)` call — `bench migrate` alone silently does nothing.** Confirmed by reading `frappe/modules/import_file.py`: `bench migrate`'s schema sync (`frappe.model.sync.sync_all()`) skips re-importing a DocType entirely whenever its own JSON file's md5 hash (`DocType.migration_hash`) is unchanged — and adding/editing a Property Setter never touches that file. So a patch that only calls `frappe.make_property_setter(..., "search_index", ...)` looks like it worked (no error, meta reflects the new value) while the actual `ALTER TABLE ... ADD INDEX` never runs, on this migrate or any later one. The real mechanism — confirmed by reading what Desk's own "Customize Form" calls after saving a Property Setter (`frappe/custom/doctype/customize_form/customize_form.py`) — is `frappe.db.updatedb(doctype)`, which re-reads the doctype's merged meta and applies the ALTER TABLE immediately and idempotently. Call it directly inside the setup function (see `create_contact_enhancements_index_property_setters` in `setup/property_setters.py`) — don't rely on the next `bench migrate` to pick it up. Verify with `SHOW INDEX FROM \`tabX\`` (via a standalone script, not `bench console` — see below), not just the meta flag.
- **Arabic first-name rules (`contact_hooks.py`) are deliberately duplicated in their `public/js/contact.js` mirror**, and both sides normalize rather than reject. Each JS mirror carries a comment pointing back at the Python docstring as the single source of truth for the rule table. This app has no JS test infrastructure at all, so keeping the two implementations in sync on any future rule change is a code-review discipline, not something automated tests catch — flag any PR that touches one without the other. Per-country phone validation (`normalize_and_validate_contact_phone`, same file) is the one exception to "mirror everything in JS" — see that section's own module docstring for why it's deliberately server-only.
- **`search_contact_by_phone` vs `search_contacts_with_details`** (`api/lead_lookup.py`) are deliberately two separate functions, not one. The first backs the native `customer_primary_contact` Link field's own dropdown and must keep its exact flat-tuple return shape. The second is the mandatory contact-picker dialog's own rich-card data (name, company, phones with channel tags). Don't merge them into one function with a "shape" flag — their shared join/filter/pagination query-building is already factored into one place, `_contact_search_query`; extend that if the shared shape ever needs to change, don't fork it.
- **`Contact Phone.country`, not `Contact.country` — the field went through both, and the first placement was wrong.** A person can carry more than one number from more than one country, and "pick a country, its rules apply" only makes sense read as applying to the number in that same row, not the whole Contact — moved down from Contact to Contact Phone (`setup/custom_fields.py`, `patches/move_country_to_contact_phone.py`) once that became clear. If a future field feels like it belongs "on the Contact" purely because that's where it was easiest to add, check whether it's actually a property of one specific number/row first.
- **A new mandatory field on a widely-shared core doctype can break a native ERPNext flow that has never heard of it — confirmed the hard way with `Contact Phone.country`.** ERPNext's own `Lead.create_contact()` (`erpnext/crm/doctype/lead/lead.py`) builds and inserts a brand-new Contact copying `lead.phone`/`lead.mobile_no` verbatim into new `phone_nos` rows, entirely inside `Lead.before_insert()` — before the Lead itself has a name, and before any Dynamic Link back to it exists, so there is no hook point in this app that can supply the real country on those rows first. Making `country` a hard `reqd=1` with no default broke Lead creation site-wide for any non-Egyptian phone number the instant this was tried. Two things fixed it without touching ERPNext core: a DocField `default` ("Egypt", this app's own established default) so the field is never *blank*, and `contact_hooks.normalize_and_validate_contact_phone` never rejecting a number just because it doesn't match the *selected* country when the number carries its own unambiguous country code — `phonenumbers.parse("+447400123456", "EG")` still correctly returns a UK number; the region argument only disambiguates a number with no country code of its own. Before adding `reqd=1` to any field on `Contact`/`Contact Phone`/`Customer`/`Lead`/`Address` (all reused by native flows this app doesn't control), check what already creates one of those records without going through this app's own hooks, and make sure it survives.
- **`Contact Phone` is in fact only ever embedded as a Table field by `Contact` itself** — confirmed by grepping every `.json` doctype definition in this entire bench (`frappe`, `erpnext`, and every custom app) for `"options": "Contact Phone"`: exactly one hit. An earlier version of this file claimed it was shared with Lead/Employee/Supplier "and others" — that was never actually checked and was wrong; corrected here so it doesn't get treated as a real constraint on some future change. Concretely: a Property Setter on a Contact Phone field *would* be properly scoped (nothing else uses this child doctype), and any doc_event registered under `"Contact": {"validate": [...]}` in `hooks.py` already covers every `phone_nos` row that will ever exist, full stop - there is no second parent doctype's save cycle that also needs the same hook. `public/js/contact.js`'s `is_primary_phone`-hiding trick (`grid.update_docfield_property` + resetting `grid.visible_columns` - see below for why that reset is needed) still works fine as implemented; it just didn't need to dodge a sharing problem that doesn't exist.
- **`grid.visible_columns` is computed once and then memoized** (`grid.setup_visible_columns()` short-circuits whenever it's already non-empty, `frappe/public/js/frappe/form/grid.js`) - `grid.update_docfield_property(fieldname, "hidden", 1)` alone only updates the underlying docfield data, not the already-rendered header row. Confirmed by testing that a hidden column stayed visible in the grid header without also clearing `grid.visible_columns = []` and calling `grid.refresh()` afterward (see `public/js/contact.js`'s own `refresh` handler).
- **A "shape" validation rule (contact_hooks.validate_full_name_has_at_least_three_words - every "Full Name" field must have ≥3 words) is deliberately NOT a blanket Contact.validate() doc_event, unlike the Arabic-name-normalization rules right above it in the same file.** Checked first: ERPNext's own native `Lead.create_contact()` sets a brand-new Contact's `first_name` to just the Lead's own single first_name field (last_name held separately) - a blanket hook would reject every native Lead-to-Contact auto-creation, the same regression class as Contact.country's own reqd=1 once caused. Scoped instead to exactly the paths this app owns: `api.contact_lookup.create_minimal_contact` (every "create a new Contact" dialog - Customer/Supplier/Employee/User all funnel through it, mirrored client-side in contact_picker_dialog.js's own primary_action for instant feedback) and a separate Employee.first_name validate hook (checked first too: the one native programmatic Employee-creation site, erpnext's own setup wizard "create employee for self", leaves first_name blank and relies on ignore_mandatory - safe, since the rule is a no-op on blank). Before adding any new "must look like X" rule to a field this app relabels/reuses, check every native flow that already writes to it, the same way - don't assume a doc_event is the only enforcement point available.
- **`frappe.ui.Dialog`'s own close ("×") button is already shown by default for any dialog not constructed with `static: true` (`dialog.js`'s own `make()`: `if (this.static) { ...; this.get_close_btn().hide(); }`)** - confirmed live across every dialog in this app: Employee/User's onboarding dialog (both `no_cancel: false` in the shared contact_picker_dialog.js, `static: !!config.no_cancel`) already have a visible, working × with zero extra code; Customer/Supplier's own mandatory dialogs (`no_cancel: true`) correctly have none, by design. Never add custom close-button markup to a dialog in this app - if one seems to be missing, check whether `static`/`no_cancel` got set (or is being inherited) unintentionally before building a replacement.
- **`config.on_before_finish`/`config.validate_extra_fields` in contact_picker_dialog.js must fire on BOTH the "create new Contact" and "pick an existing Contact" paths, not just the first one** - the original implementation only ever called them from `primary_action` (create-new only); `render_results`'s own "Select" button called `finish()` directly, skipping both. This was a real, live bug, not just an inconsistency: User's own onboarding dialog needs its Contact's `email_id`/`full_name` as a fallback specifically on the pick-existing path (nothing else in that dialog reads them there) - without the fix, picking an existing Contact silently left User.email/first_name unset. Fixed by moving both calls into `finish()` itself (called by both paths) and extracting a shared `get_values_ignoring_missing()` helper (`dialog.get_values(true)` - `true` is `ignore_errors`, not something to omit: `get_values()` with no args blocks with Frappe's own generic "Missing Values Required" popup and returns `null` the instant any `extra_dialog_fields` entry is marked `reqd: 1`, which is *also* why this app's own extra fields are deliberately never `reqd: 1` - the caller's own `validate_extra_fields` gives a clearer, field-specific message instead, but only if `get_values()` doesn't short-circuit first).
- **The cross-doctype address-inheritance chain (`utils.resolve_address_from_contact_links`, priority order Customer > Supplier > Lead > User) is wired into every doctype this app touches, not just the two (Supplier, Employee) it started with** - Customer got it as a *fallback*, tried only after its own more-specific resolution (Lead snapshot) comes up empty; Lead and User got it adapted to their own shape, since neither has a single "primary address" field to backfill - both just Dynamic-Link a resolved Address directly instead (`lead_hooks.sync_lead_address_from_contact_links`, `user_hooks.sync_user_address_from_contact_links`, the latter only ever seeding the list, never overwriting). Any new doctype this app links a Contact to should get the same treatment by default, not be left out.
- **Every doctype whose own address field is genuinely mandatory (only Customer today) needs the address resolution to happen client-side too, not just in a server-side `validate()` hook** - the same class of bug as the client-side mandatory-check race documented above: Frappe's native client-side mandatory check runs before the save request is ever dispatched, so a blank mandatory field never gives the server-side hook a chance to run. `api.contact_lookup.get_address_from_contact_links` is the shared whitelisted entry point every doctype's own primary-contact field handler (customer.js/supplier.js/employee.js) calls proactively for this - even Supplier/Employee, whose own address fields stay optional, call it for UX consistency ("sync before save" should be visible immediately everywhere, not doctype-dependent), even though only Customer is at genuine risk of the save-blocking bug.
- **A doctype's own native `quick_entry: 1` (confirmed via `frappe.get_meta(doctype).quick_entry` - User has it, Lead doesn't) bypasses `doctype_js`-driven onload dialogs entirely, the same way it bypasses `doctype_js`-driven query overrides** (see the Quick Entry `doctype_js` timing gap gotcha below) - "+ New User" showed Frappe's own short native modal (Email/First Name/Send Welcome Email) and let a User be saved without the full form - where public/js/user.js's own onboarding dialog lives - ever being reached. Fixed the same way Customer/Supplier's own Quick Entry gap was: `_disable_quick_entry(doctype)`, a Property Setter on the doctype-level `quick_entry` property, never a client-side override. Check any new doctype this app adds an onload dialog to for the same native `quick_entry` flag before assuming the dialog will actually be seen.
- **A genuine many-to-many "link multiple X to this record" relationship (User's own "Linked Addresses" section) doesn't need a new child doctype or Link field at all when the target already has its own Dynamic Link `links` table (Address does, same as Contact) - reuse that directly.** Pattern used: a Custom Field pair on the parent doctype (a Section Break + a bare `HTML` fieldtype field, `setup/custom_fields.py`), rendered/managed entirely client-side (`public/js/user.js`'s own `frm.get_field(fieldname).$wrapper`) by three whitelisted `api/user_addresses.py` functions (`get_user_addresses`/list, `link_existing_address_to_user` or `create_and_link_address`/add, `unlink_address_from_user`/remove) that just read and append/filter the target's own `links` child table - no new doctype, no new field to keep in sync. Only makes sense post-save (`frm.is_new()` guard) - a Dynamic Link needs a real `link_name` to point at.
- **A child row's own DocField default applies immediately on `.append()`, not at insert time — unlike a top-level `frappe.new_doc()`.** Confirmed empirically: `frappe.get_doc({"doctype": "Contact", ...})`'s own top-level fields stay blank until `.insert()` actually runs, but `contact.append("phone_nos", {"phone": "..."})` (no `country` key at all) already has `row.country == "Egypt"` the instant `.append()` returns. Don't assume the two follow the same timing when reasoning about whether an explicitly-omitted field will show its default yet — test it (see `tests/test_contact_hooks.py`'s `test_row_country_defaults_to_egypt` and `tests/test_lead_lookup.py`'s `TestSyncWhatsappToContact` for both directions).
- **A native "primary contact/address" Link field's own `set_query` (registered in the doctype's native `setup()`, e.g. `erpnext/buying/doctype/supplier/supplier.js`, `erpnext/selling/doctype/customer/customer.js`) is typically restricted to records already Dynamic-Linked to *this exact document* (`supplier=doc.name`/`customer=doc.name`) - always empty on a brand-new, unsaved record, since it can't be Dynamic-Linked to something that doesn't exist yet.** This app already broadens the *contact* half of that (customer.js/supplier.js's own `refresh()` overriding it to `search_contact_by_phone`), but left the *address* half (`customer_primary_address`/`supplier_primary_address`) on the native restrictive query - meaning a brand-new Customer with no Lead/Prospect/Opportunity source to auto-backfill its (mandatory!) address from could never actually pick one at all pre-save. Confirmed live and fixed by overriding it too, with an empty query (`frm.set_query("customer_primary_address", () => ({}))`), restoring Frappe's own plain unrestricted Address search - `refresh()` always runs after the native `setup()` call, so a later `set_query` call for the same fieldname simply wins. Check every native "primary X" Link field this app relabels/repositions for the same restrictive-by-default pattern before assuming it's already searchable pre-save.

## 2. Where new code belongs

| Need | Use | Why |
|---|---|---|
| Pure UI behavior — show/hide fields, defaults, formatting, dialogs | **Client Script** | Runs in the browser. Fast to iterate, but never trust it for validation or business rules — it's UX sugar, not security. It can be bypassed from the API entirely. |
| One-off, low-stakes automation you don't want to build/migrate an app for | **Server Script** (sparingly) | Runs server-side without deploying code, but it's sandboxed — no external imports, restricted Python — and hard to version-control, test, or review. Fine for a quick permission query; wrong for anything that matters. |
| Business logic, data integrity, anything performance-sensitive, anything reused across doctypes/features | **This app** | Real Python, real imports, real git history, real unit tests, full query-builder access, background jobs, caching. The only path to genuine modularity. |

Rule of thumb: if it touches the database beyond a trivial read, or you'll ever want to reuse it, it belongs in the app — not a Server Script, not a Client Script.

## 3. Design principles

- **DRY, always.** Shared logic goes in a purpose-named module (e.g. a `_dynamic_link_lookup` helper reused everywhere a Dynamic Link needs resolving) and gets imported. Never duplicate a function across files.
- **Single responsibility.** Doc_event handlers (`validate`, `on_update`, etc.) stay thin — call into a named helper, don't inline a wall of logic.
- **Every function gets a docstring** — what it does, its params, what it returns, and *why* whenever the reasoning isn't obvious from the code (this app's own history is full of subtle gotchas — see section 1 — that only a docstring prevents someone from re-breaking).
- **No business logic in client scripts.** If a client script needs to decide something non-trivial, it calls a whitelisted server method — it doesn't encode the rule in JS.
- **Client-side rule mirrors must stay in sync with their Python source of truth.** Any new client-side validation/normalization rule that duplicates server-side logic (matching the Arabic-name and Egypt-phone pattern above) needs the same explicit "single source of truth documented once, mirrored here" comment — never silently re-implement a rule in JS without linking back to where it's really defined.

## 4. Performance checklist — run this on every function that touches the database

- [ ] No `frappe.get_doc()` inside a loop. Use `frappe.get_all()` / `frappe.get_list()` with an explicit `fields=[...]` for bulk reads.
- [ ] Never call `frappe.get_all()` without a `fields` list on a wide doctype — that pulls every column, every row.
- [ ] A single-value (or few-scalar-field) lookup uses `frappe.db.get_value()`, not a full document load — a full `frappe.get_doc()` is for when you need the doc's own methods/child tables/save-cycle behavior, not just to read a handful of fields.
- [ ] Anything that could touch more than ~50-100 records runs as a background job (`frappe.enqueue`) — never inline inside a `validate`/`on_update` hook that blocks the user's save.
- [ ] Filters that will run often hit indexed columns. If a new filter needs one, flag it — add a `search_index: 1` custom field property or a DB index rather than a full table scan.
- [ ] No repeated identical DB calls inside a loop or across sibling helper functions called from the same hook — fetch once, reuse the result (e.g. load a Contact once and pass it to every helper that needs it, rather than each helper loading its own copy).
- [ ] A Dynamic Link lookup uses the shared Dynamic-Link helper, not a hand-written `frappe.db.get_value("Dynamic Link", ...)` — three near-identical copies of that exact query already existed in this app before being consolidated; don't add a fourth.
- [ ] Any client-side field that triggers a live server round-trip (`frappe.call`) has an `error` callback, not just a success `callback` — especially inside the mandatory contact-picker dialog, which is non-cancelable (`static: true`, `no_cancel()`), so a silent failure there strands the user with no way out.
- [ ] Any external API call is batched, never called once per record in a loop.

## 5. Testing

Every controller method and utils/helper function gets a `frappe.tests`-based unit test — not just a manual click-through in Desk. Tests live in the matching `test_*.py` file next to the code they cover, reusing this app's existing factory helpers (`make_lead`, `make_contact`, `make_customer`, etc. in `tests/test_lead_lookup.py` / `tests/test_customer_hooks.py`) rather than duplicating fixture setup.

## 6. Before calling anything "done"

Re-read the new code against section 4. Run `bench --site erpnext run-tests --app contact_enhancements` clean. For anything touching the mandatory contact-picker dialog or Lead-prefill logic, a real Chrome/Playwright smoke test is expected before calling it done — this app's own history has repeatedly found bugs (async races, dialog-dismissal ordering) that only showed up in a real browser, never in server-side tests alone.
